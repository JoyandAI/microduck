# TTL 总线：上电读舵机的 CRC 错误

OpenMicroDuck 的舵机和 `imu_to_servo` 走 elec_RPI_Robot_HAT 的 TTL 单线，1 Mbps，半双工。帧格式、rustypot 怎么把校验失败打出来、以及驱动里已经做的重对齐，见 [servo_communication.md](servo_communication.md)。这一页记的是：一上电、还没给舵机出力矩，`robotd` 把 IMU 和舵机收在同一笔 `sync_read` 里就很容易校验失败。R33 仍是 150 Ω 时会这样；把 R33 短接之后，同一笔还是失败。把 IMU 改成单播、舵机单独做 `sync_read` 之后，工具侧能读干净。控制环要不要改、还是这条总线本来就得分开读，还没有定。

电路说明来自 `elec_RPI_Robot_HAT_design.md` 第 6 节、第 6.1 节（原理图位号 `PCB01186`，生产文件 `ASE01187-C1`）。两份日志都在同目录：[robotd_with_crc_error.log](robotd_with_crc_error.log) 是短接前，[robotd_with_crc_error_after_shortR33](robotd_with_crc_error_after_shortR33) 是短接后。

## 短接前

2026-10-03，Radxa Zero 3W（`radxa-zero3`，`duck-57ed`），`robotd` 0.13.0，从 `/opt/robot/daemon/current` 拉起。进程一起来，短事务是通的：

```text
03:35:44.727  imu_to_servo answered on the Feetech bus id=200 attempt=1 model="0x4d44"
03:35:44.838  motor registers already correct
03:35:44.838  IMU on Feetech bus (imu_to_servo) id=200
```

ID 200 的型号探测（`0x4D44`）第一次就应答，寄存器检查也通过。紧接着每拍那次 `sync_read` 开始失败，一直到 03:37:00 按 Ctrl-C。中间没有一次干净的姿态读。

`robotd` 自己的行是启动等待，不是控制环里的 `bus read failed`：

```text
03:35:44.854  WARN  no answer from the motor bus; waiting, not commanding anything
              error=bus transaction failed: hls servo sync_read: Checksum error attempt=1
03:36:14.456  … attempt=30
03:36:45.073  … attempt=60
```

启动时读姿态每秒试一次，第 1 次以及之后每 30 次打一行（`STARTUP_RETRY_INTERVAL`、`STARTUP_READ_LOG_EVERY`）。所以屏幕上三行 WARN 对应大约 76 秒、六十多次失败。这一段守护进程只在等总线，不发力矩。

没有时间戳的 `read crc: … computed crc: … data: […]` 是 rustypot 在校验失败时用 `println!` 打的。一次 `sync_read` 里 ID 200 排在最前；第一帧校验失败它就停，所以这份日志里打出来的几乎全是 ID 200、`LEN = 17` 的 21 字节窗口。后面的关节帧不会被打印。

每次等待读一拍，这一拍内部最多试两次（`READ_ATTEMPTS`）。attempt 1 和 attempt 30 之间是 58 行，30 和 60 之间是 60 行，和「每秒一次等待、每次两行」一致。第一行 WARN 前面还有 4 行，夹在 IMU 那条日志和 attempt=1 之间的大约 16 ms 里，帧头同样是 ID 200、`LEN = 17`。

帧头经常还是齐的：

```text
read crc: 20, computed crc: 82
data: [255, 255, 200, 17, 0, 247, 255, 20, 0, 22, 0, 39, 160, 55, 40, 95, 51, 255, 254, 255, 20]
```

`FF FF | 200 | 17 | 0` 是一帧合法状态包的开头（错误字节加 15 字节数据，校验 `~(ID + LEN + ERR + DATA) & 0xFF`）。对不上的是中间的数据。载荷里反复冒出 `254`、`255`（`0xFE`、`0xFF`），那是线空闲时的高电平。另一类是窗口滑了一字节，抓到的「校验」变成下一帧的长度或空闲电平：

```text
read crc: 17, computed crc: 70
data: [255, 255, 200, 17, 0, 252, 255, 9, 0, 19, 0, 39, 160, 55, 40, 95, 51, 254, 255, 20, 17]

read crc: 255, computed crc: 231
data: [255, 255, 200, 17, 0, 2, 0, 6, 0, 24, 0, 9, 160, 65, 40, 95, 51, 127, 254, 254, 255]
```

短读能过，21 字节的状态包从第一拍起就坏，而且坏在还没出力矩的时候。[servo_communication.md](servo_communication.md) 里 K1 台架的记录是另一段：走起来之后电机电流把字节流打错位，失败会自己延续。这里的两份日志都停在启动等待，力矩还没打开。

## 短接 R33 之后

同一台 `duck-57ed`、同一个 `robotd` 0.13.0，把 R33 短接后再拉起一次。时间是 2026-10-03 04:42:14 到 04:44:12（Ctrl-C）。短事务仍然通：

```text
04:42:14.109  imu_to_servo answered on the Feetech bus id=200 attempt=1 model="0x4d44"
04:42:14.197  motor registers already correct
04:42:14.197  IMU on Feetech bus (imu_to_servo) id=200
```

紧接着每拍 `sync_read` 又是校验失败，到退出为止没有一次干净的姿态读：

```text
04:42:14.212  WARN  … Checksum error attempt=1
04:42:43.771  … attempt=30
04:43:14.354  … attempt=60
04:43:44.939  … attempt=90
```

大约 118 秒、九十多次失败，守护进程仍然只在等总线。打印形状和短接前相同：帧头是 `FF FF | 200 | 17 | 0`，载荷里有 `254`、`255`，抓到的校验经常是 20，算出来是另一个数。

```text
read crc: 20, computed crc: 129
data: [255, 255, 200, 17, 0, 0, 0, 10, 0, 21, 0, 149, 43, 143, 40, 118, 161, 251, 254, 255, 20]
```

attempt 1 到 30 之间 58 行，30 到 60、60 到 90 各 60 行，仍是每秒一次等待、每次两行。第一行 WARN 前面是 2 行，落在 IMU 日志之后大约 16 ms 里。

短接拿掉的是那 150 Ω。这次上电读的校验失败在短接之后每一拍都还在，失败的密度和字节的形状都没有变。设计说明里「有人短接 R33 后误码下降」说的是边沿变陡能压低另一类误码；它没有在这块板上消掉这份启动 `sync_read` 的校验错误。

## 分开读能过

同一天、同一台 `duck-57ed`，用 `imu_servo_read` 把两笔拆开再读：IMU 单播地址 56、86 字节（陀螺、四元数、地址 136 的加速度）；舵机单独一次 `sync_read`，地址 56、15 字节，名单里没有 ID 200。这一拍能读干净。

`robotd` 的每拍仍是一笔 `sync_read`：ID 200 排在最前，和舵机收同一块 15 字节。上面两份日志里从第一拍起就校验失败的，就是这一笔。短接 R33 没有把它变成能读的。

所以现在有两个并列的事实。合在一笔里读，启动时校验失败，原因还没找到，这可以仍是一个未解决的问题。分开读在这块板上能过，也可以就是这条总线该有的接法，控制环以后若要改，改的是「不要把 IMU 放进舵机那笔 `sync_read`」。文档停在这里，不把分开读写成控制环已经修好。

## R33 为什么会被怀疑

HAT 的 TTL 数据路径（J13、J14）是：

```text
U7 输出 / U6 输入 / R32 10 kΩ 上拉
        │
     R33 150 Ω
        │
   D4 阴极（5.1 V 稳压管到地）
        │
   TH1（冷态约 100 Ω 的 PTC）
        │
   J13 / J14 DATA
```

主机发出去和收回来的波形都经过 R33。U6 的输入在 R33 的缓冲器一侧。RS-485 不经过这颗电阻。

常态串联大约 250 Ω（150 Ω 加 TH1 的约 100 Ω），中间还并着 D4 的结电容。D4 是 `BZX384C5V1`，同封装 5.1 V 档在 0 V 时结电容大约 300 pF。1 Mbps 时一位只有 1 µs。线束加舵机 DATA 脚到 1 nF 量级时，250 Ω 的时间常数大约 250 ns，上升沿可以占掉半个位时。电平停在门限附近，采样点落在斜坡上就是误码；线上的高电平会把数据位读成 `0xFE` / `0xFF`，头还在，校验已经不对。上面那些打印就是这个形状。

有人把 R33 短接后误码明显下降，和这条路径一致：U7 改为直接驱动 D4 的结电容，插座外只剩 TH1 的约 100 Ω，两边沿都变陡。高电平最后仍停在 3.3 V。方向电路在停止位之后还要过一会儿才放开总线，回包起始处还会和主机对打一下。

上面那份短接后的日志已经做过这个试验。边沿这条解释留在这里，是因为设计说明这么写、也因为短接前的字节确实长得像采样落在斜坡上。短接之后同一形状还在，所以这份启动校验失败还要另找原因。TH1 的约 100 Ω 和 D4 的结电容在短接之后仍串在 DATA 上。

## 不要把 R33 短成 0 Ω 留在机器上

短接只适合做一次确认。这次确认的结果是校验失败还在，0 Ω 不要留在机器上，焊回一颗电阻。

150 Ω 是按 U7（SN74LVC1G126，推荐输出 ±32 mA，绝对最大 ±50 mA）的电流选的。D4 钳在 5.1 V、U7 正在拉低时，灌进缓冲器的电流约 5.1 V / 150 Ω ≈ 34 mA，已经贴着推荐值。TH1 在稳压管的插座一侧，U7 打开时它限制不住这股电流。

| 改法 | 常态串联 | 和舵机对打（约 3.3 V） | DATA 误碰电池且 U7 正在拉低 |
| --- | --- | --- | --- |
| 保持 150 Ω | ~250 Ω | ~13 mA | ~34 mA，贴着推荐值 |
| 换成 47 Ω 或 68 Ω | ~150–170 Ω | ~20 mA | 75–110 mA，超过绝对最大 |
| 短成 0 Ω | ~100 Ω（只剩 TH1） | 33–50 mA | 约 V_BATT / 100 Ω，2S 就有八十多毫安，直接进 U7 |

对打是每次回包都可能发生的。0 Ω 时这股电流已经顶到 U7 和舵机 IO 的上限。DATA 和 `+BATT` 是相邻针，母线按 5–28 V 设计，TH1 最高只有 24 V。0 Ω 时 U7 若正在拉低，电池电流几乎全部进它的下管，PTC 要热起来才断开，管脚会先坏。

设计说明里的顺序是：

1. 把 R33 换成 47 Ω 或 68 Ω，再在实际线束上测误码。47 Ω 时边沿大约快 1.7 倍，68 Ω 大约快 1.5 倍，对打电流都回到约 20 mA。误碰电池时 U7 仍可能坏，只是比 0 Ω 有余量。
2. 47 Ω 仍然不够时，换一颗结电容只有几十 pF 的 5 V ESD 管代替 D4，R33 留在 47–100 Ω。
3. 协议允许的话，把波特率降到 500 kbps 或更低。这是不动焊盘的办法。现用的每拍 15 字节回包是按 1 Mbps 放进 20 ms 节拍的，降波特率要单独看一拍还放不放得下。
4. 回包延时留几微秒，等方向电路放开总线再让舵机驱动。这不修边沿，但能减轻 R33 减小之后的对打。

这次短接已经回答了那个问题：拿掉 150 Ω 之后，上电 `sync_read` 的校验失败还在。R33 焊回电阻；47 Ω 或 68 Ω 是设计说明里为边沿准备的改法，短接试验没有给出要换小电阻的结果。0 Ω 继续留在板上，对打和误碰电池的电流都还按上一节的表走。
