一个心智模型：20 ms 的一拍

整个运行时其实只有一张动图。把下面这句话记住，后面每一讲都在填它的细节：

每 20 ms（50 Hz）一拍：先在总线上"读一次"拿到 15 个舵机 + 1 个 IMU 的原子快照 （Sensors）→ 纯计算拼出 61 维观测 → 丢给 ONNX 策略推理 → 得到 14 维动作 → 缩放成 15 个关节目标角度 → 在总线上"写一次"。 所有能"摔不坏、刷不砖"的安全机制，都是插在这条路径上、或者贴着它转的看门狗。

duck-control 是这条路径的"纯逻辑心脏"，robotd 是"守门进程"（定时器、IPC、systemd）， 其余 crate 是外围。改造飞特/IMU 时你 90% 的时间都在 duck-control + robotd 里。

2. duck-control：为什么它是"无鸭可测"的心脏

duck-control/src/lib.rs 第一段注释就是设计声明（值得背下来）：

Deliberately not a daemon. There is no tokio here, no socket, no systemd — robotd owns all of that. The boundary is enforced by the compiler rather than by discipline.

即：duck-control 刻意不碰任何进程/IO 外围，robotd 才管定时器和 socket。好处正是你要的—— 这颗"心脏"可以在没有鸭子、没有 Linux、没有 socket 的普通电脑上单独编译、单独跑全部单测。

它只有 8 个源文件，每个都短，按数据流排：

model.rs  常数表（关节编号/寄存器/默认姿势）
io.rs     RobotIo trait + Sensors + FakeIo   ← 控制循环碰物理世界的唯一边界
bus.rs    DynamixelIo：总线读/写（含 IMU 那一路）
imu.rs    SFLP 姿态解码（字节 → gyro/gravity/quat）
obs.rs    61 维观测拼装
policy.rs ONNX 策略会话与推理
safety.rs 电压/温度/摔倒 → 限幅、松力
fall.rs   摔倒预测（防"硬着陆"）

3. 关键架构缝：RobotIo（这一讲唯一要记住的概念）

duck-control/src/io.rs:113：

pub trait RobotIo {
    fn read(&mut self) -> Result<Sensors>;           // 一次事务：15 舵机 + IMU
    fn write(&mut self, targets: &JointTargets) -> Result<()>;
    fn set_gain(&mut self, kp: u16) -> Result<()>;   // "go limp"靠降增益实现
    fn set_torque(&mut self, on: bool) -> Result<()>;
    fn slow_sensors(&mut self) -> Result<SlowSensors>; // 电压/温度，约 1 Hz
    fn imu_ready(&self) -> bool { true }             // 默认认为 IMU 已收敛
    ...
}

io.rs:6 的模块注释解释了为什么 read() 把关节和 IMU 一起返回：

Sensors carries joints AND IMU together because that is what the hardware does: the IMU board sits on the Dynamixel bus and is fetched in the same transaction.

这就是你"IMU 不上伺服总线"改造要动的那条缝：现在 trait 不给 IMU 单开读口，是因为总线 本来就是一包读。等第 3 讲看完 bus.rs 你再回来看这句话，会知道为什么拆它要动哪些地方。

Sensors（io.rs:15）就是一个原子快照：

pub struct Sensors {
    pub positions: [f64; NUM_JOINTS],     // 弧度
    pub velocities: [f64; NUM_JOINTS],    // rad/s
    pub currents_ma: [f64; NUM_JOINTS],   // 只取幅值（看负载，不看方向）
    pub imu: ImuData,                     // gyro + gravity + quat
}

FakeIo（io.rs:166）是"假鸭子"：read() 把你上次 write() 的关节角度原样读回， 好像每个舵机都精确跟上了指令。单测和 robotd --fake 都用它——这就是"无鸭可测"的物理基础。

02 · 常数表与一次事务：model.rs 与 io.rs

目的：把"鸭子只是一张数据表"这件事吃透——15 个关节怎么编号、那排 EEPROM 常数为什么 动不得、RobotIo 为什么设计成"一次事务"。改造飞特/IMU 时，这两份文件是主战场。

1. model.rs：把机器人当成"数据"的常数表

duck-control/src/model.rs:1 顶部注释先立规矩：

The numeric values here are lifted from microduck_runtime's motor.rs, where they were measured against hardware rather than derived. Re-deriving them from a datasheet is exactly the kind of change that looks right and walks wrong.

记住这句话：这文件里的数不是查手册算出来的，是对着真鸭子量出来的。改它们（尤其做飞特 换装时想"按数据手册重推一套"）要三思——这是全仓最像"到处引用、一动全歪"的地方。

1.1 关节：15 个、分三组、顺序即协议

pub const NUM_JOINTS: usize = 15;
pub const JOINT_IDS: [u8; NUM_JOINTS] = [
    20, 21, 22, 23, 24, // left leg     ← 左腿 5
    30, 31, 32, 33, 34, // neck/head/mouth ← 颈/头/嘴 5（mouth 在 30–34 组内）
    10, 11, 12, 13, 14, // right leg    ← 右腿 5
];

JOINT_NAMES 不是在这里定义的——它是从 IPC 协议 crate 再导出的：

pub use duck_ipc_proto::JOINT_NAMES;     // 线上的 joints/targets 按位置索引
const _: () = assert!(JOINT_NAMES.len() == NUM_JOINTS);  // 编译期防漂移

为什么要"借用"而不是自己再抄一份？因为 Sensors/JointTargets 在线上是裸数组（按位置 对应关节），名字只给人和工具看。两处各存一份就会漂移，所以让编译期断言（const _: () = assert!） 把"长度必须一致"钉死。这是全仓贯穿的风格：用类型/断言把约定变成编译错误。

三组顺序不是随便排的——sync_read 按 ID 顺序返回块，而 bus.rs 拼 Sensors 时按 JOINT_IDS 顺序填位置，所以这个数组的下标就是关节的全局序号。索引 9 是谁？

pub const MOUTH_INDEX: usize = 9;   // = JOINT_NAMES[9] == "mouth"（有测试钉着）

鸭嘴不在任何 alpha 策略里（动作只有 14 维），所以要有个"显式的洞"让跳过 mouth 是故意的、 而不是某个 off-by-one。单测 mouth_index_names_the_mouth 保证它指向的真是 mouth。

1.2 初始姿势：和训练共用同一张表

pub const DEFAULT_POSITION: [f64; NUM_JOINTS] = [ ... 0.0, -0.0873, -0.4579, ... ];

每个值旁的注释标了是哪条腿/哪个节。要点在 doc 注释里：

Must match HOME_FRAME in the training env — a policy observes joint positions relative to home, so a discrepancy here is a constant offset on 14 observation slots.

即：策略训练时看到的是"相对 HOME_FRAME 的角度差"，真机上 obs.rs 也先减 DEFAULT_POSITION。 两边不一致 = 观测整体偏一个常数 = 鸭子看起来"站对了却莫名往一边倒"。 （microduck_rl 侧对应文件：src/mjlab_microduck/robot/microduck_constants.py 的 HOME_FRAME。 你的换装分支若改关节配置，这里和训练侧必须同一次改。）

pub const EXPECTED_REGISTERS: &[(&str, u8)] = &[

];

return_delay_time 是最关键的一行，doc 注释给了完整的算术：

The XL330 ships at 250, which is 500 µs of turnaround per device. Across 16 devices that is 8 ms per tick — 40% of a 20 ms budget — spent waiting for servos to get around to answering.

看：16 个设备 = 15 舵机 + IMU（id 200），每个省 500 µs，一拍省 8 ms。IMU 不只是被"顺带" 读的——它是这 16 设备时序预算里的一员。你把 IMU 挪下总线，这行数学从 16 变 15，check_registers （bus.rs:132）本来也只遍历 JOINT_IDS，所以那部分不受影响——但你要意识到这套时序是围着 "16 设备同包"调的。

shutdown = 52：舵机内部的错误锁存掩码（过载/过热/欠压 各占一个 bit）。这是"Dynamixel 特色"—— 飞特舵机的错误寄存器体系不同，换装时 EXPECTED_REGISTERS 整张表要换、而不是改数字。

1.4 电量：没有电量计，只能看总线电压

pub const BATTERY_FULL_V: f64 = 8.2;    // NP-F550 2S，满电带载
pub const BATTERY_EMPTY_V: f64 = 6.6;   // 低到开始吃力，还没到电芯保护

doc 注释讲清楚了：机器人没有 fuel gauge 也没有 ADC，唯一的电量读数来自舵机回报的供电电压 （"穿过总线看到的电池"），所以 8.2/6.6 是带载可用区间，不是电芯化学区间。battery_percent 必须 clamp、对 NaN/负数返回 0——单测 battery_percent_* 一排都是钉这个的。

飞特视角：恒力舵机对电压的回报、以及它的欠压/过压点，未必与 XL330 的 shutdown=52 语义一致——这套"电压=电量"映射到新舵机上要重新对着硬件标定（对应 microduck_rl 的 BAM vin=(10.5,12.6) 那套电压参数，见你的换装文档）。

2. io.rs：控制循环与物理世界的唯一边界

（第 1 讲已给 RobotIo trait 全貌，这里只补"为什么一次事务"的论证，它是你拆 IMU 的钥匙。）

io.rs:6 模块注释：

Sensors carries joints AND IMU together because that is what the hardware does: the IMU board sits on the Dynamixel bus and is fetched in the same transaction as the servos. A trait that split them would invent a distinction the bus does not have, and would double the bus traffic to honour it.

翻译成大白话：不是设计者喜欢把 IMU 塞进 Sensors，而是硬件把 IMU 放上了伺服总线。 trait 是照着硬件长的。所以当你决定"IMU 不上总线、直连主机"，你是在让硬件长出总线没有的 区别——这时拆 trait 才是正当的。第 8 讲会把它落成具体改动清单，这里先种下因果。

03 · 总线读与姿态解码：bus.rs 与 imu.rs

目的：看清"一次事务"的物理实现——一条 sync_read 怎么把 15 个舵机 + 1 块 IMU 的字节 变成弧度与 gravity；再看姿态从芯片里的 SFLP 融合块一路变到 gravity 的每一步。 这一讲是你"IMU 不上伺服总线"评估的直接依据。

1. bus.rs：同一条总线、同一包读

duck-control/src/bus.rs:3 模块注释把每拍结构说死：

One combined sync_read per tick covering the IMU board and all 15 servos, and one sync_write of goal positions. The IMU is listed first so it answers before the servo …（总线读慢速传感器是单独事务）

1.1 设备清单与一块"恰好 12 字节"的公共区

const READ_ADDR: u8 = 124;
const READ_LEN: u8 = 12;
const READ_TIMEOUT: Duration = Duration::from_millis(30);

bus.rs:114 组 ID 清单：

let mut ids = Vec::with_capacity(NUM_JOINTS + 1);
ids.push(IMU_DXL_ID);              // id 200 排第一
ids.extend_from_slice(&JOINT_IDS); // 再跟 15 个舵机

open()（bus.rs:101）用一个 serialport 打开 /dev/ttyS2，波特率 BAUD_RATE（1 Mbps）， 超时 30 ms，协议 Xl330Controller 走 Dynamixel v2。Dynamixel 的 sync_read 允许同一地址、 同一长度、多个 id 一次读出——官方利用这点，让 IMU 板和舵机都"服务"在地址 124、各回 12 字节： 舵机的那 12 字节正好是 present_pwm/current/velocity/position 连续区；IMU 板的 12 字节是 SFLP 姿态块（见下）。一次事务 16 块，全部到手。这是"一次快照"的物理真相。

1.2 read()：块怎么变成 Sensors

bus.rs:233：

fn read(&mut self) -> Result<Sensors> {
    let blocks = self.controller
        .sync_read_raw_data(&self.ids, READ_ADDR, READ_LEN) ...;
    if blocks.len() != self.ids.len() { return Err(IoError::ShortRead{...}); }

先校验块数——少一块 = 有设备没应答，直接报错而不是把旧值留一半（注释：a silently short read would leave stale values in half the joint array）。

  • blocks[0] 是 IMU（len 必须 == IMU_BLOCK_LEN 12）→ 喂给 SflpDecoder.decode()，同时过一个 StaleImuTracker：连续 STALE_RUN_WARN = 25 拍（0.5 秒）收到同一字节 → 报 "orientation is frozen"（bus.rs:257 那段，rate-limit 到每 500 拍一次免得刷爆日志）。
  • blocks[1..] 逐个拆舵机（bus.rs:269 附近）：[2..4] 电流取幅值 mA、[4..8] 速度 × RAD_PER_SEC_PER_COUNT（= 0.229 × 2π/60，datasheet 系数）、[8..12] 位置 (2π·pos/4096) − π → 弧度。

1.3 剩下的口

  • write()：sync_write_goal_position(&JOINT_IDS, &targets.positions) —— 只写位置。
  • check_registers()（bus.rs:132）：启动时只对 JOINT_IDS 断言并纠正那排 EEPROM 常数 （第 2 讲那张表），IMU 不在内。它一次 register 一读，rustypot 对单 id 也返回 Vec。
  • slow_sensors()：约 1 Hz、不在 tick 关键路径上另开事务读 144–146（电压/温度）。 io.rs 注释：pack 不会在 20 ms 内耗尽、电机不会在 20 ms 内烧起来，所以不值得每拍为它付一次事务。 电压是"穿过总线看到的电池"——model.rs 那张 8.2/6.6 电量表吃的就是它。
  • 启动路径另有 present_positions()（只读当前位置），让 robotd init 采纳机器人当前的姿势。

2. imu.rs：从 SFLP 块到 gravity

imu.rs:1 顶部注释点题，是你改造时绕不开的一句话：

One IMU, one code path. … no separate sensor to poll and no fusion to run on the host — the chip's SFLP block ships a game-rotation quaternion and estimates its own gyro bias.

融合在芯片里，不在主机上。 这是后面一切的前提。

2.1 块布局（地址 124，前 12 字节）

bytes 内容
0..6 gyro x/y/z，i16 LE，±500 dps
6..12 SFLP 四元数 x/y/z（IEEE half），w = √(1−x²−y²−z²)

完整诊断块其实是 20 字节（还带裸加速度计、采样计数、状态位），但控制循环只消费前 12， 为了塞进和舵机同一次事务——这正是"IMU 在总线上"带来的取舍。

2.2 解码：五步，每步都有注释讲"为什么"

pub const GYRO_RAD_PER_LSB: f64 = 0.0175 * PI / 180.0;  // ±500dps @ 17.5 mdps/LSB

SflpDecoder::decode()（imu.rs:103）：

  1. gyro：3× i16 LE × 量纲 → rad/s，然后用 mount（安装旋转）从传感器系转到躯干系。
  2. quat 防御：三个 half 全 0 = SFLP 还没写表（刚上电/初始化失败）→ 保留上次好值 （last_quat），绝不回落到 identity——否则摔倒检测会收到"明明姿势未知却报直立"这种最坏的谎。 校验 norm_sq ≤ 1.02 防芯片没产出的垃圾数。
  3. 把芯片四元数乘上 mount 的逆 → 躯干→世界；单位化后更新 last_quat、quat_samples += 1。
  4. gravity：gravity = normalise(rotate_inverse(last_quat, [0, 0, -1])) —— 把"世界系竖直向下" 反旋回躯干系。静止直立 = [0, 0, -1]，这正是观测与摔倒检测阈值所吃的量（ImuData.gravity）。
  5. 去尖峰：gyro 与 gravity 各自过一个 median-of-3（单拍野值被中值滤掉，比均值少滞后）。

mount 常数（imu.rs:78）：

pub const DEFAULT_MOUNT: [f64; 4] = [FRAC_1_SQRT_2, 0.0, FRAC_1_SQRT_2, 0.0]; // +90° 绕 Y

注释：board is mounted so that trunk = [+raw_z, +raw_y, −raw_x]。你直连 IMU 时，安装朝向 必须和这张表一致，或换一张新的 mount——装歪了 gravity 就错，策略与安全一起错。

ready()（imu.rs:99）：

pub fn ready(&self) -> bool { self.quat_samples >= 25 }  // ~0.25 s @ 100 Hz

直到芯片证明自己产出过融合输出之前，方向都是默认值而不是测量值——摔倒检测不许在它之前跑。 （这个 25 拍到第 5 讲会再出现：它是 odometry 播种、limp-fall 的闸门。）

2.3 对"IMU 不上总线"评估的含义

  • 若你保留 LSM6DSV16X + SFLP（直连 I²C/UART 读同一个 12 字节块）：SflpDecoder 原封复用， imu.rs 一行不用改，只换"谁把 12 字节递给它"。
  • 若换成普通串口 9 轴 IMU（无 SFLP）：第 2、4 步（芯片融合出 quat、估计 gyro bias）要你 在主机重做，还要保证输出与 ImuData 契约（躯干系 gyro rad/s + 单位 gravity + 朝向一致的 quat、50 Hz、同帧约定）逐项相等——这是第 8 讲会展开的最大风险点。

04 · 观测与策略：61 维 obs 拼装到动作缩放

目的：看懂"观测怎么拼、策略怎么跑、14 维动作怎么缩回 15 个关节目标"这条链。 这是全仓风险最高的代码——错一格不报错，只会在真机上摔倒。

1. obs.rs：61 个浮点，一格都不能错

duck-control/src/obs.rs:1 模块注释第一句就是警告：

This is the highest-risk code in the crate. It is a flat array of 61 floats whose every index must match what the policy was trained against. A wrong offset does not fail loudly — it produces a plausible-looking robot that falls over, and the symptom looks like a tuning or timing problem rather than an indexing one.

布局表（obs.rs:16 起，doc 里原文照抄）：

index   width  contents
0..3        3  gyro, trunk frame, rad/s
3..6        3  projected gravity, trunk frame, unit vector
6..20      14  joint position minus home pose, mouth excluded
20..34     14  joint velocity, mouth excluded
34..48     14  previous action, mouth excluded
48..61     13  command (below)

尾部 command 块（全 obs 里唯一没有第二真相源的部分）：

48..51      3  vx, vy, vyaw
51..55      4  neck_pitch, head_pitch, head_yaw, head_roll
55..57      2  body x, y      — always zero, unbound in training
57          1  body z
58          1  body roll
59          1  body pitch
60          1  body yaw       — always zero, unbound in training

两处极容易写错、且对着 microduck_runtime 核实过的坑（obs.rs doc 用编号列了）：

  1. body x/y/yaw 是写死 0 的——它们在训练环境里"未约束"，所以全零 body 命令是标称编码， 不是"以后会补的占位"。
  2. 头部位姿在 command 里、且不叠加到策略输出上。原型有两种模式都做、还叠加，最后用 if !new_cmd_obs + 注释 "head_offsets are a COMMAND fed via the obs vector instead — don't double-add it here" 把它关掉。两处都做会把头弯两次。

还有一处顺序陷阱：body 块是 z, roll, pitch，不是 z, pitch, roll。

1.1 嘴是怎么被"跳过"的（14 与 15 的桥）

pub const ACTION_LEN: usize = 14;              // 15 关节 − 嘴
pub const OBS_JOINTS: usize = NUM_JOINTS - 1;  // 观测里同样没有嘴
pub const COMMAND_LEN: usize = 13;

跳嘴的映射只写了一次、读写共用（obs.rs）：

const fn joint_of(slot: usize) -> usize {      // 策略槽位 → 关节下标
    if slot < MOUTH_INDEX { slot } else { slot + 1 }
}

读方向 policy_joints()（positions/velocities/home 三块同一份过滤，三块不会对不上）、 写方向 scatter_action()（把 14 维动作绕开 mouth 回填 15 个槽）都走 joint_of——

pub fn scatter_action(action: &[f32; ACTION_LEN]) -> [f64; NUM_JOINTS] {
    let mut out = [0.0f64; NUM_JOINTS];
    for (slot, value) in action.iter().enumerate() {
        out[joint_of(slot)] = *value as f64;   // mouth 的槽保持 0，不碰
    }
    out
}

为什么写这么绕？因为这里错一位 = 关节 9 之后全部平移一格，"既灾难又完全安静"。 用同一个函数的两端 + 固定宽度数组，把"对不齐"变成编译错误而不是运行时偏移。

fill() 的注释补了一个哲学：观测里出现 0 = 该关节停在 home 位。所以宁可用定宽数组让编译器 拒绝宽度不匹配，也不能用 zip（zip 在短的一侧悄悄停，尾巴留 0 → 策略对着一个"不存在的、 看起来正常的机器人"动作）。

2. policy.rs：加载期就把形状钉死

policy.rs:9 模块注释是部署安全的关键：

Everything is validated at load, not at inference. A bundle with the wrong observation width, the wrong action count, or a missing ONNX Runtime must fail while the robot is standing still — not sixty ticks later, mid stride.

所以每个网络加载时都 check_width：

check_width(path, "observation width", session.inputs(), OBS_LEN)?; // 61
check_width(path, "action count",      session.outputs(), ACTION_LEN)?; // 14

宽度不对 → 加载期就报错，robotd 把它变成"保持姿势 + 报 unhealthy + 说清原因"， 由 updater 回滚——而不是放一台动作无法解释的机器在地上跑。

2.1 网络与"谁来选"

Net 枚举（policy.rs:120）：Walk / Stand / SitStand / GroundPick / KickLeft / KickRight / Roulade。七个技能共享同一个 61 维布局——技能只是"换个 session + 换一种 command 编码"， 不是新的契约。走 vs 站由速度指令大小自动选：

pub const DEFAULT_STANDING_THRESHOLD: f64 = 0.05;   // 低于它切站

Policy 结构里 stand/ground_pick/kick_* 都是 Option<Session>——没配对应文件就是没有 这个能力，不是崩溃。哪个网络驱动这一拍是 robotd 的调度器说了算（第 6 讲见）。

2.2 对 ONNX Runtime 的防御（值得一读的注释）

ort 用 load-dynamic：编译期不需要、运行时才 dlopen libonnxruntime.so。但 ort 对"库缺失/版本不符"是 expect panic 而不是返回错误。为此 policy.rs 做了两层防御：

  • ensure_runtime()：用 libloading 在进 ort 前先探一下库能不能加载，把"缺库"变成一条 能告诉操作员的普通错误（RuntimeMissing，提示装库或设 ORT_DYLIB_PATH）。
  • catching_ort_panics()：catch_unwind 包住所有 ort 调用。注释里有个真事——一块板上 ONNX Runtime 1.20.1，探针通过（文件能加载）但 ort 在自己的版本检查里 panic (expected version >= '1.23.x', but got '1.20.1')。所以探针只证明"文件能加载"， 剩下的靠 catch 兜住，连没见过的 panic 也变成可上报错误。

还有一句部署教训写在注释里：panic = "abort" 会废掉这套——根 Cargo.toml 刻意不设 [profile.release]，加上就又把控制线程的死法改回去了。

3. 从 14 维动作到 15 个目标角度（control.rs）

动作离开 policy.infer() 后（robotd/src/control.rs），链是：

  1. 按当前状态选 (scale, gain)：走/站/roulade/ground_pick/sitstand 各有 action_scale 与 gain_ratio（tuning.action_scale 走默认 0.9、standing_action_scale 站姿、技能各自一套）。
  2. offsets = Observation::scatter_action(&action) —— 14 → 15，绕开嘴。
  3. targets[joint] = DEFAULT_POSITION[joint] + scale * offsets[joint] —— 在 home 上叠动作。
  4. 低通滤波：head_lowpass（头颈组）与 legs_lowpass（腿组）各自一个 alpha 的 EMA—— targets = α·targets + (1−α)·previous，必须等于训练侧的 ACTION_LOW_PASS_*。
  5. 写总线（RobotIo::write），拍结束。

你训练出的 ONNX 是 obs[1,61] → actions[1,14]，但缩放到关节目标的这些系数不在 ONNX 里， 在 robotd.toml / robotd-params（第 7 讲）。这就是为什么"只换 ONNX"不够、还要对参数。

05 · 安全网：摔倒预测与 limp-fall（safety.rs + fall.rs）

目的：看懂"读到的数字"如何变成"松力/保持/断电"的裁决。安全逻辑在 duck-control 里分两层： Safety（慢裁决：是不是已经倒了）与 FallPredictor（快预测：正在往下倒吗）。 这两层都吃 IMU 的 gravity/gyro——所以 IMU 怎么接、多新鲜，直接决定这层网的效果。

1. Safety：一个"门卫"对象

safety.rs 的结构一句话：Safety<T: RobotIo> 是唯一握着 RobotIo 句柄的门卫—— 主循环不直接碰总线，而是 safety.read() 读、safety.observe() 喂、safety.gate()/apply() 放行目标。doc 注释（safety.rs:17 附近）点明它的三件事：电压/温度/摔倒 → 限幅或松力， 外加对指令本身的 deadman。

1.1 配置与"先讲清它不保护什么"

pub const ACTUATOR_MIN: f64 = -PI;
pub const ACTUATOR_MAX: f64 =  PI;

注意这条注释的诚实：

This is the actuator's travel, not a per-joint anatomical limit … it catches a policy emitting NaN, an absurd action scale, or a garbage tensor; it will not stop a joint being driven somewhere mechanically unwise.

SafetyConfig 默认值（safety.rs:51）就是第 7 讲 robotd.toml 里 [safety] 的默认出处：

字段 默认 含义
fall_gravity_z -0.5 投影 gravity 的 z 高于它就"算倒"（直立≈−1.0，侧躺≈0，≈60° 处触发）
fall_debounce 200 ms 要持续这么久才算数（硬跺脚不是摔）
deadman 500 ms 指令超过这么久没更新，速度清零
gain_running 200 运行增益
gain_limp 50 松力增益：低到不再和地板较劲的那个值

1.2 裁决怎么下来

  • read()（safety.rs:127）透传给 io.read()——主循环第一件事就是它（第 6 讲）。

  • observe()（safety.rs:181）累计"gravity 越过阈值多久"：

    let down = sensors.imu.gravity[2] > self.config.fall_gravity_z;
// falling_for += dt（down 时）；任何直立样本都清零

    fall_debounce 到点 → fallen = true。单测 a_brief_tilt_is_not_a_fall 就是钉这个 （一瞬的倾斜不算）。

  • gate()（safety.rs:218）上 deadman：intent_age > deadman → 速度归零并报 Limit::Deadman。 注释/测试强调：deadman 只清 twist，别的不动（the_deadman_zeroes_the_twist_only）。

  • apply() 对每个目标做范围/有限性检查，命中就报 Limit::Range / Limit::NotFinite （枚举在 safety.rs 里，见 Limit）。

imu_ready()（safety.rs:145）透传给 bus 的 SflpDecoder::ready()（第 3 讲的 ≥25 拍）—— IMU 还没收敛前，摔倒裁决与里程计播种都不该运行。

2. FallPredictor：专门用来"提前半拍"的检测器

fall.rs:1 模块注释把为什么要第二层讲得极清楚：

[Safety] has a fall verdict already … projected gravity past fall_gravity_z (about 60° from upright) held for fall_debounce (200 ms). By the time that latches the robot is on the floor, or a few tens of milliseconds from it. That is fine for "refuse to enable a robot lying on its side" and useless for "drop the gains before it lands" — the whole value of limping is spent in the window this predictor exists to find.

Safety 回答"已经倒了吗"（用于拒绝在侧躺时使能）；FallPredictor 回答"正在往下倒吗" （用于落地前把增益降到 gain_limp，让鸭子软着陆）。要"提前"，就得看变化率而不是位置。

2.1 数学：一行叉积

躯干系里 gravity 随躯干转，所以它的导数恰好是 ġ = −ω × g，只取 z 分量就是一次乘减：

pub fn gravity_z_rate(imu: &ImuData) -> f64 {
    -(imu.gyro[0] * imu.gravity[1] - imu.gyro[1] * imu.gravity[0])
}

No filtering, no differentiation of the quaternion: the gyro is a direct measurement arriving in the same 12-byte block. —— 不去微分 SFLP quat，因为那样会把滤波器自己的 滞后加进"本该最早"的那个数里。

2.2 三个门槛 + 一小段防抖（全部满足才触发）

门槛 默认 为什么
已经倾斜过 tilt_z -0.90（≈26°） 直立时的 gyro 尖峰是跺脚/被推/被抱起，都不是摔；没有位置门槛会把三者全报成摔
还在继续倒（ġz > 0） — 在往下倒，而不是从倾斜里恢复
外推到 lookahead 后超过 predicted_z predicted_z=-0.5、lookahead=300 ms 问的是"0.3 秒后 gravity 在哪"，过了不归点才算

然后防抖 60 ms（50 Hz 三拍）——一个噪点不能让鸭子在中途失去增益。

FallPredictorConfig 完整默认（fall.rs:70 附近）就是上面那行的出处： tilt_z = -0.90、predicted_z = -0.5（与 SafetyConfig.fall_gravity_z 同号同值）、 lookahead = 300 ms、debounce = 60 ms。另外 observe() 是边沿触发：防抖到点那拍返回一次 true，之后保持 false 直到机器人不再像在倒——limp 该做多久、做完做什么由调用方（robotd）决定。

注释把调参哲学写成一句话（这是理解"为什么默认偏晚"的钥匙）：

Too early and the robot limps out of leans it would have walked off — every false positive is a fall the robot caused, which is strictly worse than the fall being dampened.

宁晚勿早：一次误触发 = 鸭子自己把自己吓倒，比摔倒本身还糟。所以 tilt_z=-0.90 平时走路 到不了，60 ms 防抖长于任何跺脚冲量、又短到能把大部分坠落留给 limp 去缓冲。

2.3 触发后：limp-fall 序列（第 6 讲在主循环里见）

robotd 在 main.rs 里看到 falling.observe() 返回真，就进入 limp_fall 状态机： 把增益降到 gain_limp、让鸭子软着陆、落地后再慢慢回到站立姿势——把"起立"这件策略最擅长的 事还给它（main.rs 那段注释："The standing policy is a good stand-up-er and a bad faller"）。

3. 对改造的含义（结合你的 IMU 直连）

这两层都假设：gyro 与 gravity 在同一份、够新鲜、够同拍的 ImuData 里到达。

  • gravity_z_rate 用 gyro × gravity 的叉积当"倒下速度"。若直连 IMU 在同拍内、只比舵机 晚几十 µs 到一两 ms 到达，这个语义基本不变；
  • 若新 IMU 刷新率比 50 Hz 低、或你改读 raw accel/gyro 自己在主机融合（滞后 + 滤波）， 这层"靠变化率提前半拍"的网会退化——ready() 的 25 拍门槛、fall_debounce、limp 窗口 全都以"IMU 足够新鲜"为前提。这是评估"不上伺服总线"时最容易低估的一环。

06 · robotd：50 Hz 主循环骨架（main.rs）

目的：前 5 讲在 duck-control 里把"纯逻辑链"讲完了——读总线、拼观测、跑策略、过 safety。 但那条链自己不会跑：是 robotd/src/main.rs 里一个 50 Hz 的 tick 在驱动它。 本讲把 main.rs 里"一拍"的完整路径走一遍：ticker 从哪来、读失败怎么办、 intent 与 safety 怎么插进来、torque 什么时候才打开。第 7 讲再进 controller 内部。

1. 50 Hz 从哪来：period 与 ticker

main.rs 顶部模块注释（repo:robotd/src/main.rs:1）一句话交代这个进程的三块：

robotd — the robot control daemon. The 50 Hz control loop, the robot.* socket, and the health the updater gates on.

控制循环跑在自己的 OS 线程 + 自己的 current-thread tokio runtime 上 （repo:robotd/src/main.rs:785 起，spawn_control_thread）。注释给了理由： 总线读是阻塞串口 I/O，放在共享 runtime 上会占住 worker；给它独享 runtime， IPC 的活儿就永远排不到一拍前面。这是整个"循环从不被客户端卡住"的地基。

1.1 period 的来处

spawn_control_thread 开头一行 let period = params.period();（repo:robotd/src/main.rs:798）。 period() 实现在 robotd-params：

pub fn period(&self) -> std::time::Duration {
    std::time::Duration::from_secs_f64(1.0 / self.control.hz as f64)
}

（repo:robotd-params/src/lib.rs:995）。control.hz 默认 50（repo:robotd-params/src/lib.rs:856）， 所以一拍 20 ms。部署文件里注释得很直白：50 Hz 是从树莓派 Zero 2W 时代继承的， 在 Radxa 上还没重新测量过（repo:deploy/robotd.toml:30）。第 7 讲细讲 params 落点。

1.2 ticker：interval(period) + MissedTickBehavior::Skip

let mut ticker = tokio::time::interval(period);
ticker.set_missed_tick_behavior(tokio::time::MissedTickBehavior::Skip);

（repo:robotd/src/main.rs:1180、repo:robotd/src/main.rs:1195）。Skip 的选择是讲稿级的细节， 代码注释（repo:robotd/src/main.rs:1181）给了测量依据：

  • Burst 把积压补发、马达指令叠在一起——显然错；
  • Delay 每拍都按 now + period 重排下一次，调度抖动全被加进周期——永久性掉速。 注释记录：用 Delay 实测 43.1 Hz 对 50 Hz 目标、missed = 0，看起来像硬件问题；
  • Skip 保持原节奏、丢弃错过的拍——控制循环要的就是这个：不积压、不漂移。

2. 两个 io：--fake 与真总线

一拍要读要写，但 io 有两个实现。spawn_control_thread 里按 args.fake 分叉 （repo:robotd/src/main.rs:817）：

if fake {
    tracing::warn!("--fake: no bus, no robot");
    runtime.block_on(control_loop(
        FakeIo::at(DEFAULT_POSITION),
        state, intents, params, period, poweroff,
    ));
    return;
}

fake 时没有总线：不给 robotd 开任何串口，FakeIo::at(DEFAULT_POSITION) 直接当 io （repo:robotd/src/main.rs:820）——每拍读回的都是"站在 home pose"的一份样本。 FakeIo 的定义注释（repo:duck-control/src/io.rs:161）说得清楚：a robot made of nothing， 读回上次写入的位置，所以驱动它的循环表现得像"舵机完美跟手"。--fake 是设计文档钦定的 笔记本路径，而且必须显式要求，不会自动降级（design §1.2 那句 must be asked for explicitly）。

真机路径在 open_bus_waiting → open_bus 里（repo:robotd/src/main.rs:857）：

let mut io = match duck_control::bus::DynamixelIo::open(port) { ... };

（repo:robotd/src/main.rs:887）。打开后还做 check_registers()——把舵机 EEPROM 里 return_delay_time/baud/pwm_slope/shutdown 校正到出厂期望值。run_init（robotd init 子命令）也直接 DynamixelIo::open(&params.bus.port)（repo:robotd/src/main.rs:743）。 类型层面用 BusIo 别名统一两种平台（repo:robotd/src/main.rs:844）： Linux 上是 DynamixelIo，非 Linux 上是 FakeIo（所以 Mac 能编译整仓、但没有 --fake 就只能得到一句 no bus on this platform; use --fake，repo:robotd/src/main.rs:915）。

每个条件都承重：sensors.is_some() 保证"读失败的那拍没有观测可拼，不拿旧数硬造一只不存在的鸭子"； !in_limp_fall 是唯一一个"不是拒绝"的条件——limp-fall 序列期间策略故意不驱动； imu_warm 挡掉"IMU 还没收敛就开步"的 crazy start。

4. 掉一拍怎么办：COAST_TICKS、连续错误与自愈

4.1 "一次掉读是寻常事"，所以必须隐形

COAST_TICKS = 3 的文档注释（repo:robotd/src/main.rs:105）讲了一个真实 bug 史： 一次失败的 Dynamixel 事务很正常——bench 实测约每分钟 8 次——但旧实现会让策略停一拍、 去命令 hold 姿势、还把 controller 重置了，于是每次掉读都变成一次可见的抽搐 （"random tiny spasms"）。3 拍 = 60 ms 覆盖"一次掉读 + 重试 + 一次慢拍"。

Coast::sample（repo:robotd/src/main.rs:2282 起）把这个语义做成一格：

Some(sensors) => { self.ticks = 0; self.last = Some(sensors); Some(sensors) }
None if self.ticks < COAST_TICKS => { self.ticks += 1; self.last }
None => None,

读到好样本就清零；连续掉读的前 3 拍吐回最后一份好样本，第 4 拍起诚实地说 None。 配套的 known_positions（repo:robotd/src/main.rs:2319）在需要"关节现在大概在哪"的场合 （hold、limp-fall 起坡）给最后读到的那组位置。coast 之所以安全，是因为观测本来就 "旧一拍"：50 Hz 下策略训练用的就是这种年龄的数据，多一拍仍在训练分布内。

4.2 连续错误：第 1 次和第 10 次才出声

let n = state.consecutive_errors.fetch_add(1, Ordering::Relaxed) + 1;
if n == 1 || n.is_multiple_of(10) {
    tracing::warn!(error = %e, consecutive = n, "bus read failed");
}

（repo:robotd/src/main.rs:1349）。掉读那拍照常跑完（coast 或 hold），日志只在第 1 次 与每第 10 次出现——持久故障可见，又不刷墙。consecutive_errors 也是健康门卫的输入： 超过 update_gate.max_consecutive_errors（默认 10）就报不健康（repo:robotd/src/main.rs:545）。

4.3 自愈：RESET_AFTER_PAUSE 决定要不要重置 controller

重新开始驱动时，controller 要不要 reset()（清空策略观测到的 action 历史、丢掉低通锚点）？ 重置本身也是个不连续。reset_on_resume（repo:robotd/src/main.rs:2331）用 RESET_AFTER_PAUSE （默认 200 ms，repo:robotd/src/main.rs:125）分界：

  • 暂停 < 200 ms（比如一次 3–5 拍的掉读）：不重置——不然会把刚想消除的抖动又引回来；
  • 真停过 200 ms 以上：重置，因为机器人可能已在别处。

注意两个常数配合：COAST_TICKS(60 ms) < RESET_AFTER_PAUSE(200 ms)，所以短暂掉读既被 coast 吸收、又够不到重置线；超过 200 ms 的停顿才当作"真的换了个世界"。

5. bringup 状态机：torque 何时开

Safety::set_torque 的 trait 注释是这个 daemon 最重要的一条不变量 （repo:duck-control/src/io.rs:132）：

Nothing calls this at startup, and that part has not changed. A robotd restarted by an update must leave a standing robot standing: torque comes on when someone enables the policy, never because a process began.

update 重启、systemd 拉起、进程崩溃重启——都不该让鸭子动一下。舵机在进程死后仍保持 最后一条目标位置指令，所以 robotd 起来后 adopt_startup_pose（repo:robotd/src/main.rs:995） 读回当前位置当作 hold，不开 torque。老设计里"开力"藏在 robotd init 子命令里 （要停 daemon、自己开总线、还没文档），于是按 Start 什么都不会发生。现在 bringup 是循环里 的一个状态机（repo:robotd/src/main.rs:959）：

Limp ──enable（策略已加载 + 有新鲜样本）──▶ Homing（torque 开，2 s 斜坡）──▶ Ready ──▶ 策略驱动

set_torque/set_gain 是每关节一笔总线事务，所以 bringup 不能是"每拍都去 apply 的 电平"，必须是"取一次请求、推进状态机"。第 11 步（repo:robotd/src/main.rs:1795）的条件很关键：

  • 从 Limp 出发；
  • snapshot.enabled（有人按了 Start / 发了 robot.enable）；
  • controller.is_some()（"enable 策略"得真有策略可 enable——否则会把坏 release 的鸭子 立起来然后傻站着）；
  • Some(sensors)（斜坡从"关节实际在哪"起步，没人读过的位置起步就是那个要避免的 lurch）。

robot.init / robot.relax 是同一个状态机的另外两个入口（repo:robotd/src/main.rs:1388）： init 不需要策略（"站起来"对没有行走网络的鸭子也合理），relax 清 enabled 并把状态机 退回 Limp。挂在主循环上的收尾状态机同理，本讲只认挂点：

挂点 位置 一句话
limp-fall（Limp→Posing→交还） repo:robotd/src/main.rs:1638 用 was_driving 而非 enabled 判定资格，防"倒地起立摇一下又触发"
shutdown-sit（坐下→断电） repo:robotd/src/main.rs:1580 电池到空（EMA）或 robot.shutdown：能坐就坐 4 s 再断 torque
mode 切换（先回 home 再换策略包） repo:robotd/src/main.rs:1538 换网络不能发生在步态中途

1. intents.rs：主循环从不问"值是多少"，只问"多新鲜"

robotd/src/intents.rs:3 的模块注释把设计一句话讲完：

Written by IPC tasks, read once per tick by the control loop. The loop must never wait on a client, so each slot is an [ArcSwap]: the reader does one atomic load and the writer one atomic store, and neither can hold up the other. Twist and head are separate slots on purpose. … Every slot is stamped, because the loop's real question is never "what is the value" but "how old is it". That is what the deadman reads.

关键词三个：ArcSwap 槽（读方一次原子 load，写方一次原子 store，互相不阻塞）、分槽（twist 与 head 分开，各自单写者）、盖章（每个值带到达时间）。最后一条是本讲第一节的主角——它不是"值 是什么"的容器，是"这值有多旧"的容器。

1.1 一个带时间戳的槽

每个槽就是一个 Stamped<T>（robotd/src/intents.rs:44）：

struct Stamped<T> {
    value: T,
    /// Microseconds since the [`Intents`] epoch.
    at_us: u64,      // 相对进程启动那一刻的微秒数
}

Intents 里 twist 与 head 各占一个 ArcSwap<Stamped<...>>（intents.rs:122），pose/mouth/skills/ power 等是别种形态，见下面的槽表。写方 set_twist（intents.rs:242）/ set_head（intents.rs:249） 每次写都带 self.now_us() 盖一个新戳：

pub fn set_twist(&self, twist: [f64; 3]) {
    self.twist.store(Arc::new(Stamped { value: twist, at_us: self.now_us() }));
}

读方只有 snapshot()（intents.rs:467）一个入口，主循环每拍调用一次，产出 Snapshot （intents.rs:184）。它做三件事：把 twist/head 值组装成 Command、把 body 钉回名义零、 算 twist_age：

pub fn snapshot(&self) -> Snapshot {
    let now = self.now_us();
    let twist = self.twist.load();
    let head = self.head.load();
    Snapshot {
        command: Command {
            twist: twist.value,
            head: head.value,
            // 姿态平滑是主循环的逐拍状态，不属于意图槽；
            // 名义零是训练编码，不是占位。
            body: BodyPose::default(),
        },
        twist_age: Duration::from_micros(now.saturating_sub(twist.at_us)),
        enabled: self.enabled.load(Ordering::Relaxed),
        pose,                      // body-pose 意图原样带上，交给主循环平滑
        mouth: f64::from_bits(self.mouth.load(Ordering::Relaxed)),
    }
}

注意 body 在 snapshot() 里永远是 BodyPose::default()（全零）——姿态意图不在这一层塞进 command，而是走 pose 字段让主循环用 cmd_alpha 平滑（§2）。这是 04 讲"body 全零是标称编码" 在代码里的确切位置。

1.2 起点就要"足够旧"：twist 从 at_us = 0 开始

Intents::new()（intents.rs:204）把初始 twist 盖成 at_us: 0，注释说得很白：

Stamped at zero, so before any client connects the twist already reads as maximally stale and the deadman holds the robot still. Starting "fresh" would mean a robot that briefly believes it has a live driver.

单测 the_twist_starts_stale（intents.rs:530）钉的正是这条：Intents 一建出来，twist_age 就从 epoch 起算，enabled == false。所以没有客户端 = 摇杆没推 = deadman 生效 = 站住，三件事是同一个 机制，不是三条约定。

1.3 槽表

意图 写方法（IPC/客户端调） 读/取方法（主循环每拍） 形态 盖不盖时间戳
速度 twist set_twist snapshot().command.twist + twist_age ArcSwap<Stamped<[f64;3]>> 盖，deadman 只读它
头 head set_head snapshot().command.head ArcSwap<Stamped<[f64;4]>> 盖，但 stale 无害
姿态 pose set_pose snapshot().pose ArcSwap<PoseIntent> 不盖，active:false 即"没人在摆"
嘴 mouth set_mouth snapshot().mouth AtomicU64（f64 的 bits） 不盖（开着就开着）
技能 skills request_skill take_skills() AtomicU32 位掩码，取走清零 事件，不是电平
上电 init/relax request_init / request_relax take_power_request() AtomicU8，取走清零 事件（一拍只做一次）

技能用位掩码而非队列的原因（intents.rs:75 附近）：20 ms 一拍内同键第二下没有额外意义，但两个 不同键都要被看见——单个 last-writer 槽会丢一个。roulade 例外：客户端每拍重发表示"还按着"， 所以它是电平，还有自己的 WHEEE_HOLD_FRESH 式新鲜度（intents.rs:101，roulade 用 ROULADE_CHAIN_WINDOW，在 control.rs 见）。

1.4 这些槽是谁写的（一句话，细节留给第 8 讲）

IPC 的 JSON-RPC handler 落到 apply_intent（robotd/src/main.rs:2631）：robot.move → set_twist([p.vx, p.vy, p.vyaw])，robot.head → set_head([neck_pitch, head_pitch, head_yaw, head_roll])，robot.pose → set_pose，robot.do → request_skill。手柄 padd 只是这些 RPC 的一个客户端——设计文档 docs/design/robotd-design.md §4.3 原话：the gamepad is a client。 socket 里怎么传、JSON-RPC 怎么分帧是第 8 讲；本讲只需知道一切命令都先落进上面这些槽。

2. 到 command 块之前：deadman 把关 + 主循环平滑

主循环拿到 Snapshot 后，先过第 5 讲的安全层 deadman（robotd/src/main.rs:1379）：

let snapshot = intents.snapshot();
let (gated, deadman) = safety.gate(snapshot.command, snapshot.twist_age);
let mut limits: Vec<duck_control::safety::Limit> = deadman.into_iter().collect();

gate()（duck-control/src/safety.rs:218）就是意图新鲜度与 deadman 的关系的全部：

pub fn gate(&self, command: Command, intent_age: Duration) -> (Command, Option<Limit>) {
    if intent_age <= self.config.deadman {
        return (command, None);
    }
    let mut stopped = command;
    stopped.twist = [0.0; 3];
    (stopped, Some(Limit::Deadman))
}

deadman 的时长来自 SafetyConfig.deadman，源头是 [safety] deadman_ms（§4）。注意它只清 twist——Snapshot.twist_age 只跟 twist 槽的戳比，head 的 stale 无害（一条注释：a stale head pose is harmless; a stale velocity walks the robot into a wall）。

gate 之后是主循环的平滑层（robotd/src/main.rs:1746 起），这是"摇杆猛推"变成"策略跟得上的 斜坡"的一步，也是 [control] 的两个参数落点：

for (ema, target) in twist_ema.iter_mut().zip(twist_target) {
    *ema += cmd_alpha * (target - *ema);        // cmd_alpha 平滑 vx/vy/vyaw
}
for (ema, target) in head_ema.iter_mut().zip(gated.head) {
    *ema += head_alpha * (target - *ema);       // head_alpha 平滑头四轴
}
// body：pose.active 时向 snapshot.pose.body 平滑；否则直接回名义零
let command = PolicyCommand {                   // PolicyCommand = obs::Command
    twist: twist_ema,
    head: [...],                                 // 还要叠 chorale 摆头
    body: BodyPose { z: body_ema[0], roll: body_ema[1], pitch: body_ema[2] },
};

cmd_alpha / head_alpha 默认都是 0.2（robotd-params/src/lib.rs:858），1.0 就是直通。 PolicyCommand 是 duck_control::obs::Command 的别名（main.rs:39）——到这里，摇杆才第一次变成 第 4 讲那个 command 块的结构：[vx,vy,vyaw] + [neck_pitch,head_pitch,head_yaw,head_roll] + body。

链路小结（本讲的前半）：robot.move → set_twist（盖章）→ snapshot 拼 Command → gate 按 twist_age 决定要不要清速度 → 主循环 EMA 平滑 → 一个干净的 Command。 这个 Command 会进 Observation::build 的 command 块（第 4 讲 61 维的 48..61）。

3. control.rs：Command → 选 Net → 动作缩放与增益

robotd/src/control.rs 是"纯计算"的心脏——模块注释第一句（control.rs:1）：

Turning sensors and a command into joint targets — and scheduling the skills. … It holds no IO handle — by construction it cannot command a motor, only propose targets.

主循环在 driving 为真时调 controller.step(...)（robotd/src/main.rs:1971），把 Command、姿态 开关、dt、电压系数 scale_mult 交给它。step()（control.rs:303）内部严格按模块注释的顺序走：

skill windows ← advance / expire (roulade window, kick timer, ground-pick phase, sit↔stand rise)
command      ← the caller's smoothed command, re-encoded for the active skill
net          ← roulade > kick > ground pick > sit/rise > stand-by-magnitude > walk
action       ← ONNX
targets      ← home pose + action_scale × action
filters      ← optional first-order low-pass on head and legs

3.1 选 Net：技能优先链 + 速度决定走/站

step() 里选网的一段（control.rs:339 起）就是第 4 讲 Net 枚举七个变体的运行时调度：

  • roulade 在跑 → Net::Roulade，effective 命令全零（训练时所有槽归零，"被选上"本身即触发）。
  • kick 窗口在跑 → KickLeft/KickRight，命令同样全零。
  • ground_pick 在跑 → Net::GroundPick，twist 槽编码相位：twist = [cos θ, sin θ, 0]， θ = 2π × phase（镜像训练端的相位编码）。
  • 否则进入坐/站/走：Sit::Sitting 把 twist 置 [1,0,0]（posture flag 坐在 vx 槽上）走 SitStand；Sit::Rising 置 [0;3] 走 SitStand（rise 命令全零所以按站立调优）；Sit::Up 才看速度：
Sit::Up => {
    if body_active { c.twist = [0.0; 3]; }      // body-pose 模式：清零速度
    let standing = self.policy.will_stand(c.twist_magnitude())
        || (body_active && self.policy.has_standing());
    if standing { (Net::Stand, c, "stand") } else { (Net::Walk, c, "walk") }
}

"走 vs 站"不是按键决定的，是速度大小决定的：will_stand（duck-control/src/policy.rs:277）= 装了 standing 网络 ∧ 未被 roller 禁用 ∧ twist_magnitude ≤ standing_threshold。阈值 DEFAULT_STANDING_THRESHOLD = 0.05（policy.rs:25），在 Policy::load(&paths, DEFAULT_STANDING_THRESHOLD) 时传进去（main.rs:1096）。这就是 04 讲那张表里"低于 0.05 切站"的出处。

方法 拒绝条件（control.rs）

3.3 缩放与增益：Tuning / SkillTuning 在每个分支怎么被消费

这是"robotd.toml 的数进到控制律"最直接的一段。step() 每拍按当前活动状态重算 (scale, gain) （control.rs:402 起），而不是像原型那样跨转换保存/恢复：

let standing_tuned = matches!(net, Net::Stand)
    || (matches!(net, Net::KickLeft | Net::KickRight | Net::SitStand)
        && self.policy.will_stand(effective.twist_magnitude()));

let (scale, gain) = match net {
    Net::Roulade => (self.skills.roulade_action_scale,
                     (self.tuning.gain as f64 * self.skills.roulade_gain_ratio).round() as u16),
    Net::GroundPick => (self.skills.ground_pick_action_scale,
                        (self.tuning.gain as f64 * self.skills.ground_pick_gain_ratio).round() as u16),
    Net::SitStand => (1.0,
                      if standing_tuned { (self.tuning.gain as f64
                                           * self.tuning.standing_gain_ratio).round() as u16 }
                      else { self.tuning.gain }),
    _ if standing_tuned => (self.tuning.standing_action_scale,
                            (self.tuning.gain as f64 * self.tuning.standing_gain_ratio).round() as u16),
    _ => (self.tuning.action_scale, self.tuning.gain),
};
let scale = scale * scale_mult;      // scale_mult：电压自适应，默认 1.0

所以"同一个 gain"在不同网络下是不同数：tuning.gain（默认 200）是行走的 P 增益；站姿/起身/ 踢球窗口是 gain × standing_gain_ratio（200 × 0.8 = 160，单测 standing_softens_the_gain 在 control.rs:524 钉着）；limp-fall 用 safety.gain_limp（50，第 5 讲）。scale 同理：行走 action_scale（0.9），站姿 standing_action_scale（1.0，the standing policy is trained to be applied whole），roulade/ground_pick 各自从 SkillTuning 取（默认 1.0，翻滚按全行走增益跑）。

scale_mult 由主循环算好传入（main.rs:1930）：voltage_adapt 打开时是 nominal_voltage / battery_v.clamp(6.0, 9.5)，默认关、为 1.0。

再往后是 04 讲已铺的尾巴：offsets = Observation::scatter_action(&action)（14→15，control.rs:432） → targets[joint] = DEFAULT_POSITION[joint] + scale * offsets[joint]（:435）→ 低通（:438）→ Ok(Step { targets, label, gain, busy })。低通用的是 tuning.head_lowpass（头颈组 5..9）与 tuning.legs_lowpass（除头颈与嘴的其余 10 个关节），None = 不过滤：

if let Some(alpha) = self.tuning.head_lowpass {
    for joint in HEAD_JOINTS { targets[joint] = alpha*targets[joint] + (1.0-alpha)*previous[joint]; }
}

3.4 主循环拿到 Step 后

controller.step 返回的 targets / gain 经 safety.apply(targets, hold, gain)（main.rs:2180）写总线。 safety 只在增益变化时才真的 io.set_gain（safety.rs:272），所以站/走切换不会每拍烧 15 次总线写。 Step.label 变成状态帧里的 policy 字段（"walk"/"stand"/"kick_left"/…），robotctl monitor 显示的就是它。

4. 参数从 robotd.toml 到强类型：robotd-params

robotd/src/params.rs 只有 7 行——它把一切 re-export 自 robotd-params crate：

//! Startup parameters — re-exported from the `robotd-params` crate.
//! The types moved out so `robotctl configure` can edit the file with the real schema, the
//! real defaults and the real validation instead of a copy that drifts.
pub use robotd_params::*;

为什么单独成一个 crate？robotctl configure（交互编辑这个文件）要跟 robotd 用同一份 schema 而不是一份会漂移的拷贝。robotd-params/src/lib.rs:1 的 crate 文档把两个关键事实钉死：

  • 读一次，不 watch：Read once at startup, not watched; live reload is deferred … any change to the file requires a robotd restart。
  • 文件在 /etc/robot/robotd.toml（DEFAULT_PATH，lib.rs:30），在 releases/<ver>/ 之外，所以 更新与回滚都不动它。policy 路径默认落在 RELEASE_DIR（/opt/robot/daemon/current，lib.rs:27）， 于是"普通更新把跟二进制一起训练的 onnx 带上来"。

4.1 TOML section → Rust 类型的映射

顶层 Params（lib.rs:34）含十个 section。跟本讲控制路径相关的：

TOML section Rust 类型 字段（节选）
[bus] Bus（lib.rs:790） port: String（默认 /dev/ttyS2，Bus::default :845）
[control] Control（lib.rs:798） hz（50）、cmd_alpha（0.2）、head_alpha（0.2），默认在 lib.rs:853
[policy] PolicyParams（lib.rs:502） enabled、mode、7 个 onnx 路径、action_scale: Option<f64>、gain: u16 …
[safety] SafetyParams（lib.rs:678） fall_gravity_z、deadman_ms、gain_limp、limp_fall_*、battery_empty_shutdown
[update_gate] UpdateGate（lib.rs:827） min_achieved_hz、stall_periods、max_consecutive_errors

每个 struct 都标 #[serde(deny_unknown_fields, default)]——多一个键要报错，但未知键的报错在 Params::load（lib.rs:920）里会被"剪掉未知键重试"的宽容路径接管（旧 build 的配置里留着新 build 没有的 [section]，不应该让 daemon 起不来；被剪掉的键会逐条 warn）。

4.2 默认值在 Default impl；resolved() 负责"没写的字段按 mode 补"

TOML 解析出来的是"文件里写了什么"，但不一定是"控制律用什么"——缺省字段要按 mode 解析。 PolicyParams::resolved()（lib.rs:605）产出 ResolvedPolicy（lib.rs:577），doc 说：

[policy] with every absent field resolved against the mode's defaults. This is what the rest of robotd consumes — nothing downstream should ever have to ask "walk or roller?" to know the action scale.

两处默认值来源要分清：

  1. impl Default for PolicyParams（lib.rs:734）：enabled: true、mode: Walk、gain: 200、 standing_action_scale: 1.0、standing_gain_ratio: 0.8、kick_duration: 0.5、 roulade_duration: 1.0……而 action_scale、head_lowpass、legs_lowpass、 ground_pick_period 等是 None——它们没有写在文件里时的兜底，而是留给 resolved() 按 mode。

  2. resolved() 里的 per-mode 分支：Mode::Walk 时 action_scale → 0.9、 head_lowpass → Some(0.5)、legs_lowpass → Some(0.7)、ground_pick_period → 4.0；Mode::Roller 时分别 0.8 / 0.5 / 0.7 / 3.0，walk 路径默认指向 alpha_*.onnx，roller 指向 roller.onnx + roller_crouch.onnx 且不装 standing 网络。

    action_scale: self.action_scale.unwrap_or(match self.mode {
    Mode::Walk => 0.9,  Mode::Roller => 0.8,
}),
head_lowpass: Some(self.head_lowpass.unwrap_or(0.5)).filter(|a| *a < 1.0),

    filter(|a| *a < 1.0) 是"1.0 = 直通 = 关"的实现——文件里写 1.0 就等于把训练带的低通关掉。

SafetyParams::default（lib.rs:766）同样是一等默认值源：deadman_ms: 500、gain_limp: 50、 limp_fall: true 等。第 5 讲的 SafetyConfig 在 duck-control 里也有一个 Default （safety.rs:68，值就是原型的数），但它主要是给单测 Safety::new(..., SafetyConfig::default()) 用； robotd 生产路径不依赖它——main.rs:1137 从 params.safety 逐字段组装，且 gain_running 用的是 [policy] gain（policy_cfg.gain）而不是 SafetyConfig 默认的 200。所以真机上"默认值只存在于 robotd-params 一处"这句话成立。

4.3 deploy/robotd.toml 就是默认值的写照

deploy/robotd.toml:1 开头写明：Every value below is the built-in default. 它装了 /etc/robot/robotd.toml 一次之后安装器永不覆盖（:9 注释：the installer never overwrites it），所以反注释掉一个值 = 那块板 永远用这个值，哪怕 release 默认值后来改了。文件里的教训原话（:24）：that is exactly how a fleet ended up standing at kP 120 while the release default said 160.

以 [policy]（deploy/robotd.toml:76）为例，它对应的就是 PolicyParams + resolved()（下面把 注释散文略去、键与默认值照抄）：

5. 改一个数从哪生效：把 gain 追到底

把整条链连起来。"改 robotd.toml 里的 gain"这句话，展开是：

  1. 编辑 /etc/robot/robotd.toml 的 [policy]，gain = 250（或 sudo robotctl configure，它用同一份 schema 写、写前用 daemon 自己的 loader 验证、原子替换——cheatsheet 保证它不能写出 robotd 起不来的文件）。
  2. 重启 sudo systemctl restart robotd。因为读一次不 watch（§4），不重启就不生效。
  3. main() 里 Params::load（main.rs:662）在启动时把 TOML 解析成 Params；--params/--port/ --no-policy 是 CLI 覆盖（main.rs:657，clap 定义在 :204）。默认路径不存在也不算错——未布板的机器 直接跑在 Params::default() 上（lib.rs:920 注释）。
  4. control_loop 前置里 params.policy.resolved() → build_controller（main.rs:1060）把 ResolvedPolicy 拆进 Tuning { action_scale, standing_action_scale, standing_gain_ratio, gain, head_lowpass, legs_lowpass }（main.rs:1070）与 SkillTuning（:1078）和 PolicyPaths（:1087）， Policy::load(&paths, DEFAULT_STANDING_THRESHOLD) 后 Controller::new(policy, tuning, skills)（:1115）。 同一个 policy_cfg.gain 又进 SafetyConfig.gain_running（main.rs:1143）。
  5. 每拍 Controller::step 按 §3.3 的 match net 消费 tuning.gain，产出本拍 gain；safety.apply 在增益变化时 io.set_gain 真写舵机（safety.rs:272）。robotd init 子命令也在自己的路径里先 io.set_gain(params.policy.gain)（main.rs:767）——它发生在 loop 之前，所以不能留上次的 gain_limp 在那儿站着。

1. duck-ipc-proto：机器人与外面唯一的"线协议"

1.0 这是什么 crate

duck-ipc-proto 是只定义线格式的 crate——顶注释写得很硬：依赖只有 serde / serde_json / semver，不碰 http、不碰 crypto、不碰 async runtime （duck-ipc-proto/src/lib.rs:1）。因为它在恢复路径上：updaterd 坏了也要能答话的 那个 crate，依赖越少越安全。

线格式一句话（lib.rs:9）：

Wire format: JSON-RPC 2.0, one object per line (NDJSON), over a unix socket. Framing is a single newline.

所以从 socket 上读到的不是二进制、不是 WebSocket，而是每行一个 JSON 对象。通知 （notification，没有 id）与请求（request，带 id）两种消息靠 id 有无区分。协议版本 API_VERSION 现在到 17（lib.rs:172）——每次不兼容改动 bump 一次，而对不上版本的 peer 不在握手时拒绝，而是让"它够不到的 route / 变了形状的 params"自己按名字拒绝 （lib.rs:50 那段注释是整个设计决策的坦白）。

1.1 关节号是"裸数组"——印证第 2 讲

lib.rs:247 有一张 15 格表，它就是线上按位置索引的真相源：

pub const JOINT_NAMES: [&str; 15] = [
    "left_hip_yaw", "left_hip_roll", "left_hip_pitch", "left_knee", "left_ankle", // 左腿 5
    "neck_pitch", "head_pitch", "head_yaw", "head_roll", "mouth",                  // 颈/头/嘴 5
    "right_hip_yaw", "right_hip_roll", "right_hip_pitch", "right_knee", "right_ankle", // 右腿 5
];

RobotState（lib.rs:2568）里 joints 和 targets 都是 Vec<f64>——光秃秃的数组， 字段注释写着 indexed as [JOINT_NAMES]。这就是第 2 讲强调的"线上按位置索引"：索引 3 是谁？ JOINT_NAMES[3] = left_knee。客户端必须带着这张表才能显示，所以这张表活在线协议里， 而 duck-control 用 pub use duck_ipc_proto::JOINT_NAMES 把它 re-export 回来，再用一个 编译期断言钉死长度（duck-control/src/model.rs:24）：

pub use duck_ipc_proto::JOINT_NAMES;
const _: () = assert!(JOINT_NAMES.len() == NUM_JOINTS);

一个 const 断言让"两条表对不上"成为编译错误。model.rs 里还有三个测试把同一件事在 运行期再钉一遍：tables_agree_on_length、ids_are_unique、imu_id_does_not_collide_with_a_joint。 你换飞特、把 IMU 请下总线之后，这些测试正是你第一个要改、且改了仍必须绿的——见第 5 节。

RobotState 其余字段也值得扫一眼，因为它们回答了"外面能看见这台机器人的什么"：

字段（lib.rs） 内容
t 单调时钟秒，用于对样、不是报时
move: { requested, applied, limited_by } 客户端要的 vs 实际放行的；被限速时 limited_by 具名（如 max_velocity）

SafetyState.gravity 有一句很关键的话（lib.rs:2649）：Projected gravity in the trunk frame, the input fallen is decided from. Upright is about [0, 0, -1]. —— 这就是第 3/5 讲 那个 gravity 出了 crate 之后的形态；robotctl monitor 屏幕上那只鸭子的倾斜、fallen 判定、 fall.rs 的预测，全部从这一个数来。

1.2 两个词汇表：intents in / state out

duck-ipc-proto 把 method 分成 namespace（lib.rs:267 起）。控制面相关的核心是两组：

  • 连续 intent：robot.move、robot.head——以 notification 发送（无 id、无回包）， 50 Hz、last-writer-wins、带时间戳（deadman 靠"它多老"而不是"它是几"）。有回包的就是错。
  • 离散 intent：robot.stop、robot.enable、robot.init、robot.relax、robot.do—— 以 request 发送、必须被回答，因为"被拒了 + 为什么"是调用方要的答案。
  • 状态流：robot.subscribe 把这条连接变成 robot.state 通知流。服务端按订阅者各自 decimate（SubscribeParams { hz }，lib.rs:1766），发布进一个有界广播，慢客户端拿到的 是空洞而不是背压——控制线程永远不等客户端。

这就是 robotd-design §1.2 那张图的接线：padd、robotctl monitor、以后的 app，全说这同一 个词汇表；mediad/btd 只是中继而不是翻译。

1.3 健康是"发布"出来的，不是"问"出来的

robot.health 的答案里有个 ImuHealth（lib.rs:2469）：

2. robotctl：从终端走 unix socket 看它

2.0 它是个"瘦客户端"

robotctl 顶注释（robotctl/src/main.rs:1）自称 A thin client：解析 argv → 连 unix socket → 发一个 JSON-RPC → 打印流式通知和结果 → 把结果映射成退出码。它里面没有任何"懂机器人"的 逻辑——逻辑全在 daemon。它用 std::os::unix::net::UnixStream（robotctl/src/main.rs:34）， 不是 tokio——短命 CLI，不需要。

socket 路径：robotctl 全局参数 --robot-socket 默认 /run/robotd.sock （robotctl/src/main.rs:82），而 robotd 的 --socket 默认值也是 /run/robotd.sock （robotd/src/main.rs:208）；真正把这些路径收口的是 duck_ipc_proto::socket 模块 （lib.rs:196，ROBOT = "/run/robotd.sock"），因为 robotctl 和 btd 都要连它，路径 每客户端抄一份就会各漂各的。

权限只有一条规则（cheatsheet 开头）：只读命令不需要特权；任何"改变机器人"的命令要 sudo。这也写进了协议——Call::is_mutating()（lib.rs:805）是 updaterd 授权用的清单。

2.1 monitor：把一个 NDJSON 流画成屏幕

monitor 订阅的就是上一节的 robot.state。robotctl/src/monitor.rs 顶注释说它是 同一个流的两种渲染，由 stdout 去哪决定：

  • 终端：一帧原地重绘的 TUI——15 个"实测角度 vs 指令角度"的偏差条、IMU 投影重力、fall 裁决、 loop 达成频率的 trace、底部健康行、右侧按实测关节姿势画的那只鸭子、最底下 odometry 的 braille 轨迹地图。q 退出，d 关鸭子，[/] 旋转视角，u 切度/弧度，t 开 ToF 矩阵， p 开手柄原始事件流。
  • 管道/文件/--json：每拍一行。落盘最常用这条（cheatsheet "Watching the loop"）：

这一行给你的是整份 RobotState、一行一个 JSON 对象——这就是为什么说 monitor 的背脊是 NDJSON 流：机器人侧 robot.subscribe → robot.state 是 NDJSON，monitor 只是挑了个终端画法。

屏幕上有三样 cheatsheet 特意点名的东西，值得记住：

  2. 健康行的最后一行是"机器人的状态而不是行为"：电量伏特与百分比、最热舵机、板温，以及 unhealthy: control loop at 43.9 Hz / degraded: no robot on the motor bus after 3 attempts / orientation frozen — 25 stale reads。最后那句只在 health 行出现、别处没有 ——"板子已停止融合但还在答总线，所以什么都不报错、gravity 永远是一个貌似合理的姿态" 正是第 1.3 节 consecutive_stale_blocks 想抓的事。
  3. 底边框点名当前加载的 policy 文件名——walk 是"两个 release 不同步态都会报的名字"， 想知道"到底是哪个网络"得看这里，而不是看帧上的 policy: walk。

3. 改造切入点 A：14 个 XL330 → 飞特 HD1910

你在 ~/microduck_rl 的评估结论（feetech_hls2915_servo_swap.md §0/§3.5）已经写清： 动作空间不变——15 关节 / 14 动作 / 61 维 obs / ONNX 契约全不动；换的是协议层、寄存器 语义、增益刻度、物理参数。这里只把它们落到 ~/microduck 的文件。

3.1 model.rs：常数表整段换语义

duck-control/src/model.rs 是"机器人=数据"的第一站，飞特换装在这里动四块：

  1. JOINT_IDS（model.rs:15）——现在是一串 Dynamixel ID 20-24 / 30-34 / 10-14。飞特 HLS 出厂 ID=1（feetech_hls_memtable.md 地址 5），你要给 15 个舵机逐一烧录唯一 ID，然后把 这张表内容换成新 ID；长度仍 15、仍按 JOINT_NAMES 索引。第 2 讲"线上按位置索引"不因 换舵机而变——JOINT_NAMES 来自协议 crate，joint_index("mouth") 照旧。
  2. EXPECTED_REGISTERS（model.rs:89）——这张表是"启动时断言并纠正的 EEPROM 寄存器"， 现在全是 Dynamixel 语义：return_delay_time/baud_rate/pwm_slope/shutdown。飞特没有 这些名字。第 2 讲点名的 return_delay_time 时序注释就在这张表头上（model.rs:84）： XL330 出厂 250 → 每设备 500 µs 往返 → 16 设备 8 ms/拍、占 20 ms 预算的 40%。飞特协议里 对应的"每帧应答开销"概念不同（帧头 0xFF 0xFF + 校验和、应答状态级别地址 8），启动检查 的哲学保留，但表内容换成飞特 EPROM：ID(5)、波特率(6)、EPROM P/D/I(21/22/23)、运行 模式(33)=0 位置伺服、保护电流(28)、卸载/报警条件(19/20)。这是一张新表，不是改数值。
  3. BAUD_RATE（model.rs:80）——1_000_000 是波特率数值；飞特那边波特率是寄存器索引 （地址 6：0=1M … 7=38400），默认 1 Mbps 恰好也是 0。DynamixelIo::open 现在把 BAUD_RATE 直接喂给 serialport::new，换协议后这个常数要么仍作串口波特率、要么新开一个 索引常量，别让两个含义混在一个名字里。
  4. 电池常数（model.rs:109）——BATTERY_FULL_V = 8.2 / BATTERY_EMPTY_V = 6.6 是按 NP-F550 2S Li-ion 标定的，而飞特是 12 V 系统（9–14 V）。battery_percent 与 [safety] battery_empty_shutdown 的"坐下去断电"联动都吃这两个数——不改的话 12 V 读数 12.4 V 会被 battery_percent 直接 clamp 成 100%，而欠压保护永远不触发。你的换装文档 §3.2 里 vin_range=(10.5,12.6) 是 sim 侧的电压域，model.rs 这两个常数是真机侧 的同一决策，两侧要一致。

3.2 bus.rs：协议整层替换

duck-control/src/bus.rs 的 DynamixelIo 是"唯一碰总线的实现"，飞特换装在这里改动最大：

  • 依赖与类型：use rustypot::servo::dynamixel::xl330::Xl330Controller （bus.rs:18）和 Xl330Controller::new().with_protocol_v2().with_serial_port(serial) （bus.rs:110）——Dynamixel Protocol 2.0 的控制器，整个换成说 FT-HLS 协议的控制器 （自己写一个薄后端，或 vendor 一个支持 HLS 的开源 SDK；你的 ftscs_protocol.md 已存档）。
  • 每一拍读：sync_read_raw_data(&ids, READ_ADDR=124, READ_LEN=12)（bus.rs:236）。飞特 反馈区在地址 56–70（当前位置 56/57、当前速度 58/59、电压 62、温度 63、电流 69/70， feetech_hls_memtable.md §2.4），不是 124。READ_ADDR/READ_LEN 和 read() 里逐字节 解码那段（bus.rs:274）都要按飞特反馈表重写。
  • 好消息：一次事务的哲学能搬。 FT-HLS 有 SYNC READ(0x82)/SYNC WRITE(0x83) （ftscs_protocol.md §4.6/§4.7），且写明"所有查询长度与首地址必须相同、应答按指令包中 ID 顺序返回"——这正是 sync_read 的语义。但协议注明"此指令针对部分串行总线舵机开放"，你的 G 阶段（actuator_physics_swap_plan.md §4 G4）要先拿单舵机验证 HLS 磁编码款支不支持同步 读；不支持就得退化成逐 id 轮询，20 ms 预算要重算。
  • 单位换算：RAD_PER_SEC_PER_COUNT = 0.229 rpm/count（bus.rs:31）是 Dynamixel 速度反馈 单位；飞特反馈速度单位是 0.732 RPM/LSB（memtable 58/59）。位置 2π·pos/4096 − π （bus.rs:287）里 4096/圈分辨率两边相同，但飞特反馈位置是 BIT15 方向的多圈 ±32767、 单圈 0.087°/LSB，且有一个"位置偏移"寄存器(31/32)定义中位——换算回 [-π, π] 的那一行要按 飞特语义重写，并和 DEFAULT_POSITION 的零点对齐。slow_sensors 的电压/温度同理：Dynamixel u16 0.1V @144 + u8 °C @146 → 飞特 u8 0.1V @62 + u8 °C @63。
  • 写目标：sync_write_goal_position（bus.rs:293）→ 飞特 SYNC WRITE 目标位置地址 42/43 （0.087°/LSB、多圈 BIT15 方向）。

3.3 增益：不是同一个单位

set_gain(kp: u16)（bus.rs:304）现在写 Dynamixel 的 position_p_gain、并把 I 和 D 写 0—— 那段注释（bus.rs:305）说得很清楚：Dynamixel 的 RAM 增益每次上电回出厂、出厂 D 不是 0，所以 写 0 是刻意的。飞特这边：

  • 位置环增益是 Kp@50（1/8 缩放）、Kd@51（1/4 缩放）、Ki@52（位置模式无效），上电由 EPROM 21/22/23 赋值（memtable §2.3）。"每次上电要重写 SRAM 增益"这个时序逻辑保留，但"写哪些 寄存器、值域 0–254、带缩放"全是新的。
  • safety 里"limp = 把增益降到 50"、正常跑 200（io.rs:122 附近）——这两个数字是 Dynamixel 刻度；换到飞特 0–254 + 1/8 缩放的刻度，gain_limp/默认增益的数值要重定，而且换装文档 要求 Kd 显式写、且与 sim 建模一致（feetech_hls2915_servo_swap.md §1.1：BAM 是 P-only+ 反电动势，真机却带 D）。这不是搬数值，是把"软/硬"的刻度整个翻译一遍。
  • 第 2/4 讲讲过的低通与"下发即到"假设要重新审视：飞特固件有目标速度+加速度"缓起缓停" （ACC@41，0=最大加速度；SPEED@46/47），50 Hz 下发的目标在真机内部按斜坡追——策略训练假设 "20 ms 内目标基本到位"，慢舵机 + 固件限幅会引入额外的相位滞后。sim 侧建模是 ~/microduck_rl 的活（你的 §3.1 HD1910Actuator），运行时侧要意识到：同一份 obs 布局，喂给 策略的 joint_pos/joint_vel 的时间语义变了。

4. 改造切入点 B：IMU 从伺服总线上拿下来直连

4.0 现在的结构

imu_to_dxl v2 板（LSM6DSV16X）以 id 200 骑在 Dynamixel 总线上，和舵机共享同一根 UART， 在同一个 sync_read 里读回（robotd-design §1.1 那张图）。io.rs:6 的模块注释把这件事说成 了 trait 的形状：

[Sensors] carries joints and IMU together because that is what the hardware does: the IMU board sits on the Dynamixel bus and is fetched in the same transaction as the servos. A trait that split them would invent a distinction the bus does not have, and would double the bus traffic to honour it.

第 3 讲讲过"为什么拆它现在才正当"——当时不正当，因为总线没给理由。你把它请下总线， 这句话的前提就没了："硬件就是这么做的"不再是事实，拆 IMU 源才是诚实的建模。

4.2 两条路线，一条明确推荐

路线①：保留 LSM6DSV16X + SFLP 芯片，只换传输。 芯片仍在片内跑 SFLP，输出 fused quaternion + gyro；你只是把"这 12 字节从哪来"从"总线块 124"改成"第二个串口/另一路"。imu.rs 的 SflpDecoder（half() 解码、rotate/median3_each、DEFAULT_MOUNT、ready() 门限） 整体搬运、几乎不改。obs 第 0..6 格（gyro 3 + projected gravity 3）的单位和坐标系不变， safety/fall 直接续命。真正工作集中在传输层 + 时序。

路线②：换普通串口 IMU（裸 accel/gyro）。 现在片上的 SFLP 融合要搬到主机端——要么自己写 互补滤波/Madgwick，要么找带自带四元数的模块；gyro bias、温度、安装角全部重新标定； ready() 的语义（"融合已收敛"）要重新定义。obs 的前 6 格、fall 的解析导数前提 （ġ = −ω×g，gyro 与 gravity 同源同拍）都可能被滤波滞后破坏。这是风险最大的一条。

明确建议：走路线①。 你的 RL 侧两个文档都只重舵机、没碰 IMU/obs 语义——路线① 完美贴合 "架构不动"的前提：decode、mount、obs 布局、安全裁决全不动，只把 id-200 那一支从伺服总线挪到 一个新源。路线② 是把"别人做好的融合"变成"你要在 50 Hz 主循环里养的另一个滤波器"，那是 一整类新风险，和换舵机叠在一起会让故障无法归因。

4.3 真正的坑：ready / stale 语义迁移，而不是解码

三个数字现在互相咬合，全建立在"50 Hz、同一总线、同一拍"上：

  • SflpDecoder::ready() = quat_samples >= 25（imu.rs:99），注释说约 0.25 s；
  • bus.rs STALE_RUN_WARN = 25（=半秒）；
  • duck_ipc_proto ImuHealth::FROZEN_RUN = 25（=半秒，lib.rs:2496）。

IMU 离开总线后：新源的采样率可能不是 50 Hz（SFLP 板现在约 100 Hz 内部刷新、你 50 Hz 采样）， 读时刻和 tick 不再锁相，"连续 25 块相同"的含义、ready() 要等多久、stale 计数在哪个线程更新 ——这三个数/三处代码要一起搬、一起重定，否则 monitor 的 orientation frozen — 25 stale reads 会在新硬件上要么永远不响、要么开机就误报。这正是你 ~/microduck_rl/docs/ 换装文档的 空白：feetech_hls2915_servo_swap.md 和 actuator_physics_swap_plan.md 都只在运行时一行 带过"协议层全换"，没有任何一节写 IMU 直连。建议补一节，标题就叫 「直连 IMU + 复用 SflpDecoder + obs/安全语义不变」，内容至少覆盖：路线① vs ② 的取舍、 SflpDecoder/StaleImuTracker/imu_ready 三件套迁到新源、25 这个数在新时基下的重算、第二 端口的 systemd/权限。

5. 下刀顺序与规模评估

一次把话说清：官方代码改动面在 4 个文件 + 1 个新协议后端，不是全仓。

下刀之后，"语义没被破坏"的机器读法是：同一批测试（更新到新常数表后）依然全绿。要区分两类 测试——凡是写死"XL330 刻度 / id 200 在总线上 / Dynamixel 寄存器名 / 124 号块布局"的，必须 改写成新契约（这不是作弊，是用测试把新契约钉下来）；凡是保护不变量的——obs 偏移、 嘴跳过、scatter 回填、安全裁决、stale 计数结构——必须原样绿。一批测试里哪些"应该变"、 哪些"必须不能变"，本身就是改造设计的一部分。
